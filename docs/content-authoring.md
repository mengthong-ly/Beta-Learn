# Writing lessons, guide chapters and quizzes

This is the **reference** for the file format. For the step-by-step procedure — setup, numbering,
verifying — see [adding-a-lesson.md](adding-a-lesson.md).

Content is Markdown on disk. There's no CMS and no database — a lesson is a file, and
`npm run check:content` is the test suite.

```
content/<course>/lessons/NN-slug.md   lessons, ordered by the numeric prefix
content/python/guide/NN-slug.md       the Guide Book (only Python has one so far)
```

The file's slug (`NN-` stripped, `.md` stripped) becomes the URL and the storage key. **Renaming
a file orphans every learner's progress and drafts for that lesson**, and renumbering means
updating every cross-link by hand.

## Rule zero: check the official source first

Never write a lesson from memory. Check the behaviour against the official reference, and add a
short **Reference** link at the end of the lesson pointing at the page you used.

| Course | Source |
| --- | --- |
| Python | <https://docs.python.org/3/>, <https://docs.python.org/3/whatsnew/> for 3.14, <https://peps.python.org/> |
| PHP | <https://www.php.net/manual/> |
| Laravel | <https://laravel.com/docs/13.x> |
| TypeScript | <https://www.typescriptlang.org/docs/> |
| React | <https://react.dev> |
| Dart / Flutter | <https://dart.dev>, <https://docs.flutter.dev> |

Per-course source lists live in `.design/thonglearn/research/courses-research.md`.

## Lesson anatomy

````markdown
---
title: The compiler
section: 1 · The Basics
---

Prose. Markdown with GFM. Fences in the course's language get a **Try it** button.

```typescript
const message = "hello!"
console.log(message.toUpperCase())
```

## Challenge

> 🎯 **Challenge:** Fix the bugs the compiler reports so it logs `Hello Maddison, it is 2026!`.

```typescript starter
console.log(greet("Maddison", launch.getFullyear))
```

```typescript solution
console.log(greet("Maddison", launch.getFullYear()))
```

```typescript check
expect(output[0] === "Hello Maddison, it is 2026!", "Log exactly: Hello Maddison, it is 2026!")
```

**Reference:** [The Basics](https://www.typescriptlang.org/docs/handbook/2/basic-types.html)
````

### Frontmatter

| Key | Required | Notes |
| --- | --- | --- |
| `title` | yes | shown in the sidebar and the page title |
| `section` | yes | groups lessons. `"2 · Strings & Lists"` → section id `2`, which is also the section quiz's id |
| `summary` | guide chapters | one line, shown on the Guide Book index. Required for a chapter; a chapter also needs 3+ runnable examples |

### Fences

`<lang>` is the course's `lang` from `lib/courses.ts` — `python`, `php` (Laravel too), `typescript`,
`tsx` (React), `cpp`, `dart` (Flutter too).

| Fence | Meaning |
| --- | --- |
| ```` ```<lang> ```` | a runnable example. Gets **Try it**, and `check:content` runs it |
| ```` ```<lang>-snippet ```` | a fragment that isn't a whole program. Not run, no **Try it** |
| ```` ```<lang> starter ```` | the editor's starting code. Pulled out of the prose |
| ```` ```<lang> solution ```` | must pass the check |
| ```` ```<lang> check ```` | the verdict (see below) |
| ```` ```quiz ```` | the lesson's questions. Pulled out of the prose |
| ```` ```text ```` | anything else — output, diagrams, pseudo-code. Never run |

An example that's *meant* to fail must say so with an `error!` comment on the failing line, e.g.
`message() // error! This expression is not callable.`. `check:content` asserts it really fails.

### Callouts

| Prefix | Renders as |
| --- | --- |
| `> 💡 **Tip:**` | sky |
| `> ⚠️` | peach |
| `> 🎯 **Challenge:**` | lavender — used to introduce the challenge |
| `> ✅` | mint |

| `> 🔍 **Behind the scenes: …**` | a **collapsible**; its first paragraph is the always-visible title |

## Checks

A check decides whether the challenge is solved. It runs *after* the learner's code, in a wrapper
generated by the runner, with the lesson's output already captured. Helpers differ per runtime:

| Course | Available in a check |
| --- | --- |
| Python | `__stdout__` (everything printed, as one string), plus the lesson's own globals. Use `assert …, "message"` |
| PHP, Laravel | `$output` (a string), `expect($ok, $message)`; Laravel also has `visit($uri)` returning a `Response` |
| TypeScript, Claude Code | `output` (`string[]`, one entry per `console.log`), `expect(ok, message)`, `lesson.*` for anything the file exports |
| C++ | `output` (`std::vector<std::string>`), `expect(ok, message)`, the lesson's own functions and types |
| Dart | `output` (`List<String>`), `expect(ok, message)`, `lesson.*` |
| React | `$`, `$$`, `click(el)`, `type(el, value)`, `tick(ms)`, `expect(ok, message)` — the check runs against the live DOM |
| Flutter | the body of a `testWidgets` test: `tester`, `find`, `expect`, and the app already pumped |

Write the failure message for the learner, not for you: `"Line 1 should be 'Hello, Python!' but
was …"` beats `"assertion failed"`.

Two rules `check:content` enforces:

- the **solution** must pass the check
- the **starter** must *not* pass it — otherwise the challenge is already solved

## Quizzes

A `` ```quiz `` fence at the end of a lesson. Parsed by `lib/quiz.ts`.

````markdown
```quiz
? easy: What does `print(1, 2)` show?
+ 1 2
- 12
- 1, 2
> print() puts sep=" " between values.

? medium: What does this print?
~~~python
print("a", "b", sep="-")
~~~
+ a-b
- a b
- a\nb
> sep replaces the space between values.
```
````

- `? easy|medium|hard: <prompt>` starts a question. Inline `` `code` `` is allowed.
- `+` is the correct answer — exactly one per question. `-` are the wrong ones. At least two
  options total.
- An optional `~~~` block turns it into a "what does this print?" question. `check:content` runs
  that code and compares it with the `+` answer, so a wrong key fails the build. In code
  questions, `\n` in an option means a real newline.
  **Python and C++ only so far** — a `~~~` block in any other course fails the check with
  *"quiz code questions are only verified for Python and C++ so far"*. To support another course,
  add its case to `assertOutput` in `scripts/check-content.ts`.
- `> ` lines are the explanation, shown after answering; consecutive lines are joined.

Section and final quizzes are assembled automatically from lesson questions:
a **section quiz** takes up to 10 medium/hard questions spread across its lessons, the **final**
takes up to 8 medium + 12 hard from the whole course. Nothing to author.

## XP and progress

`lib/stats.ts`: 10 XP per completed lesson, 2 per best lesson-quiz point, 50 per section quiz
passed, 200 for the final. Streaks count consecutive local days with any activity.

## Verifying

```bash
npm run check:content                  # every course — slow
npm run check:content -- php dart      # just these
```

It runs every example for real: Python in Pyodide (anything on stderr — including a pandas
`FutureWarning` — fails, and the Inspect collector runs too), the local courses on your
toolchains, React transpiled and server-rendered. React *checks* need a live DOM, so those are
only verified in the browser — `check:content` reports them as `unverified` and skips the
"starter must fail" rule for them.

If you changed content in a `local` course (Dart, Flutter), you need
`npm run setup:runtimes` and the toolchains first. See [runtimes.md](runtimes.md).

### Recorded outputs (Dart)

On the website, Dart and Flutter lessons are write-only. Under each example, learners get
"Predict: what happens when this runs?" and then the **real** output, and the solution comparison
shows what the solution prints. Those outputs come from
`npm run check:content -- --record <course>`, which writes `content/<course>/outputs.json`
(keyed by a hash of each example's code). After you add or change an example or a solution in
Dart, re-record and commit the file; `check:content` fails when a recording is missing.
Flutter isn't recorded: it prints nothing worth showing.
